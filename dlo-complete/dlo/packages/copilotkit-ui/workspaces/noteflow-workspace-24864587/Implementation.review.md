> Reviewer: built-in

## Suggestion 1 — Multi-user editing has no conflict resolution [severity: high]
**Rationale:** The entire premise of `WorkspaceService`/`PageShareRepository` is that multiple people work in the same workspace and can be granted write access to the same pages. Nothing in m12 (`PageTreeService`) or m13 (`BlockService`) addresses what happens when two members edit the same block or move the same page concurrently — both go straight to a `updateFields`/`move` write with no version check. That's a silent last-write-wins data-loss bug in the product's core collaborative use case, and it will surface the first week real users share a workspace, not in some future "real-time collab" phase.

**Proposed change:** In m13's acceptance criteria, add: *"`updateBlockContent` and `moveBlock` accept an expected `updatedAt`/version token from the client and throw `ConflictError` (not silently overwrite) when the current row's version doesn't match, with a unit test covering the stale-write rejection."* Add the corresponding `updated_at`/`version` column to the affected tables in m3 if Database.md doesn't already carry one. This doesn't require building full OT/CRDT sync — it just prevents blocks/pages from silently clobbering each other, which is the minimum bar before shipping multi-member workspaces.

## Suggestion 2 — No password-reset / account-recovery flow [severity: high]
**Rationale:** m9 (`AuthService`) and m18 (auth routes/UI) ship `signUp`, `login`, `verifySession`, `logout` — and nothing else. There is no forgot-password, no email verification, no way to recover a locked-out account. This isn't a v2 nicety; it's table stakes for any product with real user accounts, and shipping without it means every user who mistypes or forgets their password is permanently locked out with no support path built in.

**Proposed change:** In m9's **Build** section, add: *"`requestPasswordReset(email)` (issues a single-use, time-limited token via `SessionRepository` or a new `PasswordResetRepository`, no-ops silently on unknown email to avoid enumeration), `resetPassword(token, newPassword)` (validates token, re-hashes, invalidates all existing sessions)."* Add matching routes to m18 (`src/routes/forgot-password.tsx`, `src/routes/reset-password.tsx`) and acceptance criteria covering valid-token reset, expired-token rejection, and unknown-email non-enumeration. If email delivery is genuinely out of scope for this pass, the plan should say so explicitly rather than omit the feature silently — per this codebase's own "no silent fallbacks" principle, a stubbed-out reset flow must be labeled, not absent.

## Suggestion 3 — m17 collapses the entire backend fan-out into one serial join before any UI can start [severity: medium]
**Rationale:** Section 3 of the Build Order correctly parallelizes m9–m16 (eight services, several marked `hard`/`medium` complexity, with m13 given `maxAttempts: 4` because it's expected to need retries). But m17 depends on *all eight* of them, and every UI module (m18–m22) depends on m17. That means the single flakiest, hardest service in the batch (likely m13 `BlockService`, already flagged as retry-prone) gates 100% of UI work from starting — a five-module backend fan-out narrows to a one-module bottleneck right before the highest-LOC phase of the project.

**Proposed change:** Split `container.ts` construction so `withAppContext` and the auth-only slice of the container (needed by m18) can be assembled as soon as m9–m11 (Auth/Permission/Workspace) are done, without waiting on m12–m16 (page-tree/blocks/database/view/search). Concretely: change m18's `dependsOn` from `["m17"]` to a new lighter `m17a` (auth-only container) built right after m9–m11, and keep the full `m17` (all services) as a dependency only for m19–m22, which actually need `PageTreeService`/`BlockService`. This lets auth UI start ~3-4 modules earlier instead of waiting on the hardest services in the plan.

## Suggestion 4 — Repository layer is never tested against real Postgres [severity: medium]
**Rationale:** m8's acceptance criteria explicitly mock the Drizzle client (correctly, per the testing policy — no real DB in unit tests). But that means the plan's riskiest SQL — the recursive CTE in `findSubtreeIds`, the generated `search_vector` columns, the partial unique indexes on `pages.position` — is *never* exercised against a real Postgres instance anywhere in this document. Mocked-client tests verify the repository calls the right Drizzle methods, not that the SQL Drizzle generates actually executes or returns correct results. A syntax error in the recursive CTE or a misdeclared generated column would sail through every unit test in this plan and only surface in production.

**Proposed change:** Add a new module (e.g. `m8b — Repository integration smoke test`, depending on m8 and the Docker-provisioned Postgres from the DB_PROVISIONING_RUNNING phase) with acceptance: *"A `tests/server/db/repositories/integration.test.ts` (tagged to run only when `DATABASE_URL` is set, skipped otherwise) runs the real migration against the Docker Postgres instance and exercises `findSubtreeIds`'s recursive CTE, both `search_vector` generated columns, and the partial unique index conflict path against real rows."* This can run as an exit clause during `DB_PROVISIONING_RUNNING`/`TESTING_RUNNING` rather than in the default `npm test` unit run, keeping the mandatory-unit-test policy intact while closing the gap.

## Suggestion 5 — Scope: this is a full Notion clone with no stated wedge [severity: medium]
**Rationale:** 22 modules ship page trees, a full block editor with slash commands, rich text runs, a database feature with table/board views, fractional indexing, workspace roles, and sharing — essentially Notion's entire core surface area in one pass. Nothing in this document states what the differentiating wedge is or why *all* of this needs to ship before the first real user sees the product. Database views (m14/m15/m21) in particular are the most complex, highest-risk slice (`hard` complexity, cross-cutting validation rules) and could be deferred to prove out the page/block/sharing core first.

**Proposed change:** Either (a) add a one-paragraph note at the top of the Build Order stating the product bet this scope is testing (e.g. "workspace-based collaborative notes with structured data views, targeting X users who currently use Notion for Y"), so the scope is a deliberate choice and not just "build everything Notion has" — or (b) cut m14/m15/m21 (DatabaseService/ViewService/database UI, ~3 of 22 modules) from this pass and ship page-tree + block-editor + sharing + search as v1, adding database views once the core is validated. As written, a reviewer can't tell whether the database-view feature is essential or scope creep, and it's the single largest chunk of "hard"-rated work in the plan.

## Overall Verdict

The engineering discipline here is genuinely strong — the DAG sequencing, universal typed-error vocabulary, mandatory-test acceptance criteria on every module, and the deliberate "test harness before any consumer" ordering (m1→m2) are all things I'd want to see in any plan. My concerns are less about execution quality and more about product completeness and risk placement: the plan is confident about UI polish (slash menus, drag-and-drop, rich text toolbars) but silent on the two things that will actually determine whether this product survives contact with real users — concurrent-edit safety and account recovery — and it defers all real-database verification to trust in mocks. I'd want suggestions 1 and 2 addressed before this ships to anyone outside the team, and I'd want an explicit answer on suggestion 5 (is the database-view feature essential to the bet, or is it the fastest thing to cut if the timeline slips) before greenlighting the full 22-module scope as a single build.

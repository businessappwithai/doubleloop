## Suggestion 1 — Unverified core dependency: the entire UI layer is built on `@astryxdesign/*` [severity: high]
**Rationale:** Every frontend module (m1, m16, m18, m19, m20, m21 — half the plan) depends transitively on `@astryxdesign/core`, `@astryxdesign/theme-neutral`, `@astryxdesign/build`, `@astryxdesign/cli`. If this is not a real, actively-published, React-19-compatible npm package, `m1`'s `npm install` fails on module 1 of 21 and the entire build fleet never starts. Betting the whole scope on an unverified/obscure dependency before a single line of code runs is the single largest risk in this plan, and it's invisible until execution begins.
**Proposed change:** Before dispatching the fleet, add a zero-cost pre-flight check: `npm view @astryxdesign/core @astryxdesign/theme-neutral @astryxdesign/build @astryxdesign/cli` (or equivalent registry lookup) to confirm the packages exist, are maintained, and declare React 19 as a supported peer. If they don't check out, replace the phrase in m1/m16 — *"@astryxdesign/core, @astryxdesign/theme-neutral, @astryxdesign/build, @astryxdesign/cli, @stylexjs/stylex"* — with a verified, actively-maintained pairing (e.g., raw `@stylexjs/stylex` plus a known component layer, or drop the constraint and let m16 hand-roll primitives on StyleX alone). Do this verification once, centrally, rather than letting m1 discover it after the fleet is already running.

## Suggestion 2 — Real-time collaboration is the plan's largest risk surface and may not be core to the product [severity: high]
**Rationale:** "Engineering Knowledge Workspace" reads as a personal/team wiki: organize concepts, edit docs, search, sync to Git. Yet three of the hardest modules in the plan (m11's Yjs CRDT persistence, m13's standalone websocket relay server, m19's client-side awareness/presence/reconnect-backoff) exist purely to support live multiplayer cursors — and they sit on the critical path: m13 blocks m15 (assembly), m19 blocks m21 (the final route wave). If collaboration breaks (it is genuinely the hardest thing in the whole plan — CRDT convergence, debounced snapshot persistence, reconnect backoff under fake timers), the *entire app* fails to ship, even though search, hierarchy, editing, and Git-sync — the actual knowledge-workspace value — don't need it.
**Proposed change:** Change the sequencing note *"Wave 3 — the domain modules (m9, m10, m11, m12, in parallel; then m13, m14)"* and *"m19 (Yjs provider + awareness/presence)... run in parallel"* so that m13 and m19 are explicitly marked optional/deferred: m15's orchestrator wires collaboration behind a feature flag (`config.collab.enabled`), and m21's concept route renders `CollaborationPluginBridge` + `PresenceBar` conditionally. This lets m15/m21 land and the app ship even if m13/m19 blow their `maxAttempts`, instead of an all-or-nothing dependency chain.

## Suggestion 3 — Hardest algorithmic work is assigned to the cheapest execution tier with only 3 attempts [severity: high]
**Rationale:** Per the pipeline's own conventions (build fleet = haiku), modules like m10 (fractional-index tree allocator + advisory-locked subtree moves + recursive-CTE ancestor paths), m11 (Yjs CRDT merge correctness across two in-process docs), m15 (topological registry + schema stitching + non-throwing GraphQL orchestrator), and m18 (Lexical custom `DecoratorNode`s with markdown-shortcut `NodeTransform`s) are exactly the kind of subtle, invariant-heavy code that cheap models get wrong in ways that *pass a shallow test* but fail the real invariant (e.g., a `keyBetween` allocator that satisfies the 100-insertion test but collides on insertion 101 in production). `maxAttempts: 3` on "hard" complexity with no escalation path risks silent, expensive failure loops.
**Proposed change:** In the machine-readable plan, add a per-module `executorTier` override for m10, m11, m13, m15, m18, m19 (the six modules independently flagged `"estimatedComplexity": "hard"`) — e.g., `"executorTier": "claude-sonnet"` instead of the default haiku fleet — or, if tier can't be overridden per-module, add a rule to `phases/build.ts` that escalates the executor after attempt 2 fails rather than retrying identically a third time. Cheap-model correctness on CRDT and locking code is not a place to economize.

## Suggestion 4 — No module builds authentication; `Actor` resolution has no source [severity: medium]
**Rationale:** `RequestContext`/`Actor` (m3) and "actor resolution" in the GraphQL route (m15: *"method check, body parse, request-id assignment, actor resolution, delegation"*) are referenced throughout — presence entries carry `actorId`, Git-sync commits need an author, collab rooms are authorized per actor — but no module in the plan issues sessions, verifies credentials, or establishes identity. As written, `m15`'s "actor resolution" step has nothing upstream to resolve against.
**Proposed change:** Either add an explicit module (e.g., `m4b — Auth: session issuance and actor resolution middleware`) between m4 and m9, or make the scope decision explicit in the document rather than implicit: change m15's acceptance bullet *"the route returning 405 for GET, 400 for a malformed body, and 200 with `errors`"* to also state *"actor resolution reads a dev-only header/stub identity (`x-actor-id`); real authentication is out of scope for this build and tracked as a follow-up"* — so reviewers and the eventual user aren't surprised that anyone who can reach `/api/graphql` is any actor they claim to be.

## Suggestion 5 — Automated Git push has no human checkpoint [severity: medium]
**Rationale:** m14's Git-sync worker stages, commits, and **pushes** to an external repository on an injected-timer schedule with no approval step — `"stages, commits and pushes through the GitPort, records a run row, and on failure records the failure and rethrows"`. This is the one place in the generated app that mutates state outside its own database, on a repeating schedule, autonomously. A bug in `link-rewriter.ts` or the frontmatter serializer could push malformed/corrupted content (or leak a draft concept) to a shared remote before anyone reviews it — and per this repo's own CLAUDE.md, irreversible/external-facing actions are exactly the category that should sit behind a gate, not run silently on a timer.
**Proposed change:** Add to m14's acceptance criteria: *"the first Git-sync run after deploy defaults to `dryRun: true` (writes the file set and computes the diff but does not push) until an operator flips `config.gitSync.autoPush`"* — giving the product a human-reviewed first sync instead of trusting an unreviewed cheap-model-built exporter with write access to a real repo from day one.

## Suggestion 6 — m1 commits the entire dependency graph atomically with no fallback if it doesn't resolve [severity: low]
**Rationale:** The stated rationale — *"so that no later module ever has to edit `package.json` dependencies and race another module for that file"* — is sound for avoiding file contention, but it means a peer-dependency conflict anywhere in the stack (React 19 + Relay + Lexical + Yjs + StyleX + the unverified Astryx packages, all pinned together) fails module 1 with no incremental fallback; the other 20 modules simply never run.
**Proposed change:** Keep the single-`package.json`-owner design (it's correct), but change m1's acceptance criterion *"npm install completes and npx tsc --noEmit exits 0"* to require the install log be captured and, on `ERESOLVE` failure, retried once with `--legacy-peer-deps` before failing the module — cheap insurance against a known-common npm 9+/React 19 peer-dependency friction point, without redesigning the wave structure.

## Overall Verdict
This is an unusually well-engineered *process* — the wave structure, the fake-ports-first sequencing, and the non-negotiable per-module test attribution are genuinely excellent practices that most engineering orgs don't enforce even with human authors. But as a CEO reviewing scope and risk, the plan bets the entire 21-module build on three compounding gambles: an unverified niche design-system dependency at the very first module, real-time CRDT collaboration (the hardest possible feature) sitting on the critical path for a tool whose core job is organizing and searching text, and cheap-tier execution assigned to the hardest algorithmic modules with no escalation path. None of these require re-architecting the plan — they require de-risking the dependency before launch, making collaboration optional rather than load-bearing, and adding a human checkpoint before the app autonomously pushes to a real Git remote. Fix those three and this is a strong plan to execute as-is.

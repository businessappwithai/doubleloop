# CEO Review — Architecture.md

> Reviewer: built-in

## Suggestion 1 — No phased MVP; the whole system ships as one atomic scope [severity: high]
**Rationale:** The document specifies 11 modules (bundles, concepts, hierarchy, documents, frontmatter, search, collab, git-sync, plus UI), a CRDT collaboration server, a Relay/GraphQL layer, and a Git export worker — all as a single "Build contract" with no ordering, no milestone that could ship and be used before every module exists. Combined with the 90/90/85/90 coverage gate and "no `--passWithNoTests`," this reads as: nothing is usable until everything is built and fully tested. That's a large time-to-first-feedback risk for a tool whose core value (can an engineer actually find and trust a concept?) can be validated with a fraction of this scope.

**Proposed change:** Add a "Delivery Phasing" section before "Central Orchestrator" that sequences the modules into at least two milestones, e.g.:
- **Phase 1 (single-user, walking skeleton):** `core`, `ports`, `BundleModule`, `ConceptModule`, `HierarchyModule`, `DocumentModule` (no CRDT — plain optimistic-concurrency save), `FrontmatterModule`, `SearchModule`, GraphQL/Relay read+write, `SidebarTree`/`ConceptEditor`/`FrontmatterPanel`/`SearchPanel`. Ship this behind the same coverage gate.
- **Phase 2 (collaboration + sync):** `CollabModule`, the `y-websocket` server, `GitSyncModule`, `PresenceBar`.

State explicitly that Phase 1 is deployable and demoable on its own, and that `DocumentModule.save`'s `expectedVersion` optimistic-concurrency path (already specified) is sufficient for single-user editing, so Yjs is additive, not a prerequisite.

## Suggestion 2 — GitSyncModule only exports; there is no import path for existing OKF bundles [severity: high]
**Rationale:** The scope line says this is "specialised for Google Cloud's Open Knowledge Format (OKF)," implying interoperability with an existing ecosystem of Knowledge Bundles. But `GitSyncModule` (§10) only has `planExport`/`writeExport`/`syncBundle` — write-only. There is no `importBundle` or `ingest` capability anywhere in the module list, `BundleModule`, or the folder layout. If a customer's whole reason for adopting this tool is "we already have OKF bundles in git, let us edit them here," this architecture cannot onboard that data at all — only produce new bundles from scratch and push them out.

**Proposed change:** Add an `import(ctx, repoDir): Promise<ImportReport>` method to `GitSyncModule` (or a new `BundleImportModule` depending on `frontmatter`, `concepts`, `hierarchy`, `fs`, `git`) that walks a checked-out OKF repo, parses each `.md` file via `core.parseOkfDocument`, and creates/updates the corresponding `Concept` tree. Add a corresponding `syncBundleToGit`-style mutation's counterpart, `importBundleFromGit`, to the GraphQL schema in the "GraphQL conventions" section, and add its test requirements (malformed frontmatter mid-import, partial-failure rollback, idempotent re-import) to the Testing Strategy section 3.

## Suggestion 3 — No authorization model despite this being a multi-user collaborative product [severity: high]
**Rationale:** `Actor` appears in `RequestContext` and `Provenance.author` exists, but nothing in the document says who is allowed to create, edit, or delete a Concept, set a bundle's Git remote, or trigger a sync/push to a real Git remote. For a "collaborative" workspace this is a blocking product gap, not a nice-to-have — without it, any authenticated actor can rewrite or delete another team's bundle, or push to a Git remote they shouldn't have access to. The `syncBundleToGit` mutation in particular is a real-world-effecting action (pushes to an external remote) with zero access control specified.

**Proposed change:** Add an "Authorization" subsection under "Central Orchestrator → Responsibilities" defining a `can(actor, action, resource)` check invoked by the orchestrator's request-lifecycle step before delegating to a module (per rule 2, this keeps modules free of authz branching). At minimum, gate: bundle delete, `setGitRemote`, `syncBundleToGit`, and `updateFrontmatter` lifecycle transitions to `archived`. Specify where `Actor`'s roles/permissions come from (the document never says — SSO claims? a `users`/`roles` table?) and add it to the `sql/migrations` list and the config schema.

## Suggestion 4 — GitSyncModule pushes to a shared remote on an unconditioned timer, with no lifecycle gate [severity: medium]
**Rationale:** "Deployment Shape" states the Git sync worker runs "in-process timer in the app server, gated by `GIT_SYNC_ENABLED`" every `GIT_SYNC_INTERVAL_MS`. `GitSyncModule.planExport` takes `ConceptExportRow[]` with no filter mentioned — meaning `draft`/`unverified` concepts get exported and pushed to the team's real Git remote alongside `active`/`human-reviewed` ones. For an engineering knowledge base other tools or people may consume via that git repo, silently publishing half-written drafts on a 5-minute timer is a credibility and correctness risk, and there's no described way to pause sync for a single bundle mid-edit.

**Proposed change:** In the `GitSyncModule` section, change `planExport`'s contract to `planExport(concepts, { minLifecycle: Lifecycle })` (default `"active"`), and document the default as excluding `draft`. Add a per-bundle `syncPaused: boolean` column and a `pauseSync`/`resumeSync` mutation so an author mid-edit can suppress a push. Add the corresponding test case to §"Per-layer coverage requirements → 3": "`planExport` excludes concepts below `minLifecycle`."

## Suggestion 5 — Mandatory 90/90/85/90 coverage with zero phase-in tightens the delivery risk from Suggestion 1 [severity: medium]
**Rationale:** "A red test suite blocks the build. There is no path by which an untested module ships." is a strong and good quality bar, but paired with a big-bang scope (Suggestion 1) it means *nothing at all* ships until the entire 11-module, CRDT-plus-Git-sync system clears 90% line/function coverage. This is a sequencing conflict the document doesn't acknowledge: the quality bar is right for what ships, but it should be a gate per phase/module, not a gate on the whole system reaching feature-completeness first.

**Proposed change:** Reword the "Definition of done (per module...)" block to make explicit that the gate applies per-module/per-PR, not only at final system assembly: add a sentence "CI enforces this per merged module from day one — coverage is checked incrementally as modules land, not deferred to a final full-system pass," and cross-reference the phasing added in Suggestion 1 so leadership understands quality is continuous, not a closing gate that delays the first deployable slice.

## Suggestion 6 — Mandated "AI-fluent" design system, but no AI-assisted feature anywhere in the product [severity: low]
**Rationale:** The Astryx justification cites "AI-fluent manifests" as a reason for the design-system choice, and the product is named an "Engineering Knowledge Workspace" in 2026, where the baseline expectation for a knowledge tool is at least semantic search or AI-assisted authoring/summarization. Nothing in `SearchModule` (containment + full-text only), `ConceptEditor`, or elsewhere touches embeddings, an LLM call, or a summarization/suggestion feature. If the "AI-fluent" capability is being paid for (as a dependency and as design-system lock-in) but never used, that's scope waste; if it's simply out of scope for v1, the document should say so explicitly rather than gesturing at it via a throwaway justification line.

**Proposed change:** Either (a) strike "AI-fluent manifests" from the Astryx justification row since it's not exercised anywhere in this document, or (b) add a one-line explicit "Out of scope for this build: AI-assisted search/summarization; Astryx's AI-fluent manifest support is adopted for future use, not implemented here" note under "Explicitly rejected," so reviewers don't infer an AI feature exists when it doesn't.

## Overall Verdict
The technology choices are well-justified and the engineering discipline (ports/adapters, typed errors, orchestrator-as-composition-root, exhaustive test strategy) is genuinely strong — this is a document a team could build from without ambiguity. The CEO-level risk is entirely about scope and sequencing, not engineering quality: the plan commits to shipping a fully-collaborative, CRDT-synced, Git-round-tripping, 90%-covered system as one indivisible unit, with no import path for the very OKF bundles it's meant to interoperate with, and no access-control model for a supposedly multi-user product. Fix the phasing (ship single-user CRUD+search first), close the import gap, and add an authorization layer before this goes to a build fleet — those three changes reduce the time-to-first-value and close the biggest "this doesn't actually do what we need yet" risks without touching the sound technical foundation underneath.

## Suggestion 1 — Real-time collaboration and Git sync are full v1 scope, not staged — this is the highest-risk over-build in the document [severity: high]
**Rationale:** The schema commits to CRDT collaborative editing (`yjs_updates`, `collab_sessions`, compaction jobs, presence) and bidirectional Git sync (`git_remotes`, `git_sync_runs`, `git_sync_files`, a scheduler, credential handling) as core, launch-blocking infrastructure — migrations `004` and `007` are in the same numbered sequence as identity and the concept tree itself. That is two genuinely hard distributed-systems problems (CRDT merge correctness, Git worker idempotency/credential handling) bolted onto a product that, per the dev seed, has never had a real user (`ada@example.test`). Nobody has validated that "Engineering Knowledge Workspace" needs live multiplayer editing before we've validated that it needs an editor at all. If collaboration turns out to be a nice-to-have rather than the reason people adopt this, this is 3 tables, 2 background workers, and non-trivial ongoing operational surface (compaction, stale-session reaping, active-run uniqueness) built and maintained for nothing.
**Proposed change:** Split the migration set into a v1 core (`001`–`003`, `005`–`006` minus collab-dependent indexes, `concept_documents` without `crdt_state`/`crdt_state_vector`/`compacted_through`) and a v2 "collaboration + sync" set (`004`'s CRDT columns, all of `007`). Ship v1 with last-write-wins + `version` optimistic concurrency only — which the document already builds as a first-class primitive — and gate real-time collab and Git sync behind evidence that users are hitting the single-editor limitation or asking for git-backed export. Add one sentence to the doc's header: *"CRDT collaboration and Git sync are phase-2 scope, deferred until single-editor usage validates demand; `concept_documents.crdt_state` and the `007` migration are written but not applied until that gate is met."*

## Suggestion 2 — There is no monetization or organization primitive anywhere in the schema [severity: high]
**Rationale:** Fifteen tables model identity, hierarchy, content, collaboration, and Git sync in exhaustive detail, but there is no `plan`, `subscription`, `seat`, `organization`, or `usage` concept anywhere — `workspace_members.role` (`owner`/`admin`/`editor`/`viewer`) is the entire access/business model. For a product this document treats as production-grade (SLA-level session timeouts, 10s statement timeout, advisory-lock serialization), the absence of *any* answer to "how does this generate revenue and how do we meter it" is a scope gap a CEO has to flag before more schema gets built on top of it — retrofitting billing onto `workspaces` after bundles/concepts/git_remotes already reference it is a much more painful migration than adding it now.
**Proposed change:** Add a minimal `organizations` table above `workspaces` (or confirm workspace *is* the billing unit and say so explicitly) plus a `workspace_plan` row: `plan_tier text NOT NULL DEFAULT 'trial'`, `seat_limit integer`, `storage_limit_bytes bigint`, `trial_ends_at timestamptz`. It does not need enforcement logic yet, but its absence should be a documented decision, not a silent gap. Replace the current opening line *"Fifteen tables plus the migration ledger"* with an explicit note: *"No billing/plan entity exists yet — `workspaces` is the sole tenancy unit and monetization model is undecided. This is a deliberate deferral, not an oversight."*

## Suggestion 3 — `ON DELETE RESTRICT` on every `created_by`/`author_id` reference to `users` means a user can never be deleted while they have content, with no erasure path [severity: high]
**Rationale:** `workspaces.created_by`, `bundles.created_by`, `concepts.created_by` all reference `users(id) ON DELETE RESTRICT` specifically "so audit trails cannot be silently erased." That's a defensible design for audit integrity, but the document never describes the corresponding erasure/anonymization path a real product needs (GDPR Art. 17, CCPA deletion requests, or just "an employee leaves the company and asks to be forgotten"). Right now the only documented lever is `is_active = false`, which deactivates login but leaves `email` and `display_name` — PII — permanently queryable and irremovable as long as the user has ever created a workspace, bundle, or concept, which for any real usage is effectively always. This is exactly the kind of gap that turns into a fire drill during a customer's security review or a real deletion request, not a theoretical concern.
**Proposed change:** Add an explicit anonymization procedure to the `users` section: *"Erasure requests are satisfied by anonymization, not row deletion: `UPDATE users SET email = 'deleted-' || id || '@deleted.invalid', display_name = 'Deleted User', avatar_color = '#6b7280', is_active = false WHERE id = $1`. `created_by`/`author_id` FKs remain intact (satisfying audit-trail integrity) while no PII survives. This is the documented resolution for GDPR/CCPA erasure requests and is the only sanctioned way to remove a user's identity from the system."* Reference this from the `RESTRICT` rationale so the two decisions read as one coherent policy instead of one being silently unaddressed.

## Suggestion 4 — `yjs_updates` has no database-enforced ceiling between compactions, only an application-level timer [severity: medium]
**Rationale:** Each row is capped at 4 MiB (`CHECK (octet_length(update_bytes) BETWEEN 1 AND 4194304)`), but the *table* has no bound: compaction is triggered by "a timer and whenever the tail exceeds `config.collab.compactAfterUpdates`" — entirely in application code. If the compaction worker crashes, falls behind, or a client bug spams updates (each up to 4MB, on an append-only unindexed-by-size table), nothing in the schema stops `concept_id`'s tail from growing without bound, which directly threatens the `statement_timeout = 10s` on the recursive ancestry query and any full scan touching this table, and is a real storage-cost exposure once this is a paid product (Suggestion 2). This is the collaboration feature's actual failure mode, and the document only describes its happy path.
**Proposed change:** Add a CHECK-adjacent safety valve to the `yjs_updates` section: either a partial index the reaper can alert on — `CREATE INDEX yjs_updates_uncompacted_idx ON yjs_updates (concept_id, id) WHERE id > (SELECT compacted_through FROM concept_documents WHERE concept_id = yjs_updates.concept_id)` (or simpler, a periodic count query the operational runbook checks) — or an explicit stated limit: *"If a concept's uncompacted tail exceeds 10,000 rows, the collaboration server refuses new connections for that document and forces synchronous compaction before accepting further updates, raising `ResourceExhaustedError('collab.compactionBacklog')` to the client."* Right now there is no such statement anywhere.

## Suggestion 5 — No audit log for workspace membership/role changes or Git credential reassignment, which will block enterprise sales for a product literally named "Engineering" workspace [severity: medium]
**Rationale:** `concept_revisions` gives excellent content-level audit history, but there is no record of *who* promoted a user to `admin`, changed `git_remotes.credential_ref` (i.e., repointed where the org's source-of-truth docs get pushed, using whose token), or removed a workspace member. For a product targeting engineering teams — who will ask security-review questions like "show me who had admin access on date X" during any serious procurement process — this is a known, specific, and common blocker, not a hypothetical one. `workspace_members` and `git_remotes` both have `updated_at` but no history.
**Proposed change:** Add one small append-only table reusing the pattern `concept_revisions` already establishes: `CREATE TABLE audit_events (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, workspace_id uuid NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE, actor_id uuid REFERENCES users(id) ON DELETE SET NULL, event_type text NOT NULL, subject_type text NOT NULL, subject_id uuid, detail jsonb NOT NULL DEFAULT '{}'::jsonb, created_at timestamptz NOT NULL DEFAULT now());` populated on role changes, `git_remotes` credential/repo_url changes, and member add/remove. This is cheap now (one table, no new module) and expensive to retrofit once there's real membership history to reconstruct.

## Suggestion 6 — The document never states a backup/PITR or disaster-recovery posture for what is positioned as the single, canonical store of the org's engineering knowledge [severity: low]
**Rationale:** Every operational detail in this document is meticulous — statement timeouts, advisory lock keys, GIN pending-list tuning — except the one question a CEO evaluating "can I trust this to hold my company's docs" will actually ask first: what happens when the Postgres instance is lost or corrupted. `crdt_state` and `body_markdown` are the only copies of unpublished edits (Git sync only covers what's already been exported), so a backup gap here is a data-loss risk, not just an availability one.
**Proposed change:** Add a short "Backup & Recovery" subsection under Overview: minimum stated commitment, e.g. *"Continuous WAL archiving with 5-minute RPO, daily base backups retained 30 days, PITR tested quarterly via `pnpm db:verify`'s disposable-container path restored from a real backup rather than a fresh migration run."* Even a one-paragraph placeholder turns this from "clearly never considered" into "explicitly deferred, tracked."

## Overall Verdict

The engineering craftsmanship here is genuinely excellent — the hybrid concept/document/frontmatter split, fractional-index sort keys, composite FKs enforcing same-bundle parentage, and the `jsonb_path_ops`-only containment discipline are all the right calls for the problems they solve. But that is precisely the CEO-level concern: this document solves hard *engineering* problems (CRDT merge, Git bidirectional sync, tree-move serialization) with production-grade rigor while leaving open the *business* problems (how do we bill for this, what happens when a customer asks us to delete a user, what's our restore story, how do we sell to security-conscious engineering orgs) essentially untouched. Before more schema gets poured on top of `workspaces`/`bundles`, get explicit sign-off on deferring collaboration and Git sync to a validated phase 2 (Suggestion 1), and close the compliance and monetization gaps (Suggestions 2–3) now, while they're a paragraph and a table instead of a migration against live customer data.
